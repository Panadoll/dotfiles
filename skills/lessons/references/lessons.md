# 复盘与教训记录

复盘记录“最近的改动哪里做错了，用什么规则本可以拦住”。结果写在仓库根目录的 `LESSONS.md`，`AGENTS.md` 要求改代码前先读它。

Agent 提交频繁的仓库最需要复盘：同样的错误会在不同会话里反复出现，而每个会话都不记得上一次。

## 什么时候做

- 定期做，按提交量定节奏：一天几十个提交就每天一次，少的每周一次。
- 一次大返工、一次回滚或一次线上问题之后，不等周期，马上做一次。

一次复盘筛选 `reviewed-through` 之后的提交，同时复核上期摘要里仍缺证据的存疑项；同一个修复提交不要重复计数。标记记录筛选进度，不代表每个候选都已确认。

## 修改范围

只改 `LESSONS.md`、代码规范文件（默认 `docs/code-standards.md`，仓库已有同类文件就沿用），以及 `AGENTS.md` 的入口。子系统参考页只写代码当前保证的行为、每条都有源码出处，由维护它的流程负责，复盘不改；教训是“以后应该怎么做”的规则，不属于那里。复盘期间不改产品代码：发现还没修的 bug，报告给用户或开 issue。

## 步骤

1. **定范围。** 读 `LESSONS.md` 第一行的 `reviewed-through`。没有这个文件就是第一次复盘：范围取最近一个周期，用户指定了就按用户的；没指定时取最近 50 个提交，或最近一周，取少的那个。然后按下面的模板新建文件。
2. **找返工候选。** 运行（Windows 上把 `python3` 换成 `python`）：

   ```bash
   python3 <技能目录>/scripts/rework.py --root <仓库根> --since <reviewed-through>   # 之后每次
   python3 <技能目录>/scripts/rework.py --root <仓库根> --last 50                     # 第一次
   ```

   脚本对每个提交追溯它改写的行是哪个提交写的，列出改写了 72 小时内刚写成代码的提交，以及回滚提交。每个提交只出现一次，下面列出它改写了哪些提交的多少行，产品代码和测试分开计数。修复类提交排在前面；只改写了近期测试行是弱信号，不等于整个提交只改测试。默认不算文档文件，`--include-docs` 可以加上；移动或重命名文件按旧路径追溯，只算真正改了的行。范围超过 `--max-commits`（默认 400）时脚本报错且不输出标记，调大上限后重跑，不要跳过较早的提交。浅克隆的 blame 不可靠，脚本会拒绝运行，先 `git fetch --unshallow`。脚本给出的标记是扫描时的 `HEAD`，所以下一期不会重扫已经合并进来的分支提交。

   用合并提交（merge commit）合并 PR 的仓库，分支上的分步提交也在范围里，PR 内部的迭代会成为候选，按下面“明确分步”的标准判断，不要直接算返工。
3. **再找脚本看不到的线索。** 脚本只看行级改写。还要看：
   - 提交说明或 PR 里写着“又”“再次”“漏了”“follow-up”的；
   - 重新打开的 issue、同一个 issue 被多个提交引用的；
   - 超出已确认范围、违反既定决策、合并检查未通过或验证声明缺少证据的；
   - 同一天里对同一功能的多次发布。

   查 CI 时，绑定实际被合并版本的 PR head SHA，以 `mergedAt` 为界核对当时要求的检查：只把合并前已完成且通过的检查算作已验证，后来的绿色重跑不能倒推合并时已通过。取消或未完成不算通过，但是否违反合并要求仍要核对当时约定；查不到记录就写证据不足。

   没有远程权限、查不了 issue 和 CI 时，只用 git 历史做，并在本期摘要里写明“未查 issue 和 CI”。
4. **逐条判断。** 从信号最强的候选开始。返工候选要读前后提交的 diff 和当时的范围说明；只有证据能连成这条链才算返工：原提交当时应满足什么行为 → 它引入或在声称修复时遗漏了什么缺陷 → 后续提交如何修正同一个缺陷。`git blame` 只说明谁最近写过这些行，不证明谁引入了缺陷。

   明确分步且没有破坏当时约定的行为、支持新增调用方、重构或格式化，都不算返工；没有写分步计划也不自动算错。后续提交叫 `fix`、提到“补齐”，或很快改写同一文件，都只是线索。证据不能区分缺陷与范围扩展时，列为“存疑”，写明哈希和缺什么证据，不计入教训；也不要直接归为正常。

   “挑几条”按脚本输出里的提交计，一个提交下面列了几个被改写的提交也只算一条。

   一次返工指一个修复提交加上它修的那个（或那几个）提交。同一个修复提交改写了几个早先的提交，仍然只算一次。

   合并把关失误、验证不足即使没有后续修复，也能形成教训，但要指出违反了哪项已确认的范围、决策或验证要求，并附对应提交与事实证据。没有新增自动测试不等于验证不足；没有运行记录只能证明记录缺失，不能推断从未验证。这类问题单列，不计入返工次数；无法确认就存疑。
5. **归纳成规则。** 把已确认的问题按“如果当时遵守哪条规则就不会出错”归类。规则写的是一类错误，换一个功能也用得上；具体的文件、函数、功能名放进证据里，不写进规则：

   | 不好：只是重述这次事故 | 好：一类错误的规则 |
   | --- | --- |
   | 改 `update.sh` 时要重启所有工作进程 | 判断运行中的进程要不要重启，不能只看它读的文件有没有变；启动时加载的配置和开关，文件 diff 里看不出来 |
   | `--intent` 要写清自洽性 | 拆分一个字段的职责时，同一个改动里写清新字段必须独立成立的条件，不能留到下一个 PR |

   规则要能照着检查，例如“修一处时搜一遍同样写法的兄弟代码，一起修”，而不是“更仔细一点”。
   - 已有的教训又出现了：在那条下面补证据和日期，更新天数；近重复条目合并，不另起一条。
   - 新的：按模板新增一条。
   - 只关乎某个子系统的规则（例如“这个缓存键必须带租户 ID”），也写进 `LESSONS.md`，在主题里注明子系统，不改参考页。如果代码或测试已经保证了这条约束、参考页却没写，在汇报里指出，留给下次改这个子系统或巡检时补进参考页。
6. **也记做对了的。** 有提交明显做对了（复现了报告者的原始场景、一次修全了所有同类、写清了手动破坏过什么），在对应教训下记一行“做对的例子”。这比只记错误更能教会下一个 Agent 该怎么做。
7. **升级。** 一条教训累计出现 3 天（可以跨多次复盘累计），就把规则移进代码规范，带上最有代表性的证据。`LESSONS.md` 里把它挪到“已移入规范”一节，只留一行和日期。评审照代码规范检查，所以升级之后这条规则在每次评审里都会被检查。

   `LESSONS.md` 每次会话都要读，无论是否升级，重复事故只保留最有代表性的叙述，其余证据压成日期和哈希；不得丢失累计日期的依据或未解决的存疑项。旧摘要也压缩叙述，不重复展开教训正文。
8. **写本期摘要，推进标记。** 在标题下、第一个主题之前追加一段，不加单独的标题：本期范围和提交数、返工候选数、已读及未读数、返工/正常/存疑数、主要问题、升级的教训和未查的线索；合并把关或验证问题另列，不混入返工数。每个已读候选只用一行：哈希、分类、一句话理由（可引用已有教训）；存疑附证据缺口。摘要数应与条目相符，返工比例不是质量目标。脚本成功且摘要写完后，才替换第一行的标记。
9. **提交。** 只提交上面修改范围内的文件，单独一个提交。本期没有新证据时，只推进 `reviewed-through`，摘要里写“本期无新教训”。

## 证据要求

- 每条证据都要有提交哈希，必要时附 issue 或 PR 编号。写之前用 `git show <哈希>` 确认它确实是你说的那样。
- 写清错在哪和可核对的后果；返工还要写后来怎么修、隔了多久。“`<哈希A>` 只修了一个调用方，`<哈希B>` 两天后补上另外三个”，而不是“修得不完整”。没有修复记录就写未知，不编造。
- “出现”按出错提交的日期去重，不按修复日或发现日。9 月 3 日的 B 修了 9 月 1 日的 A，就记 9 月 1 日（`git show -s --format=%cs <A>`）。同一个修复对同一条规则只记一天；涉及多个出错提交时，取已证实最早引入该问题（或声称修复却遗漏它）的提交日期。无法确定就存疑，不猜日期。同一天的多次返工只算一天，但都可以列为证据。
- 日期一律取提交者日期（`%cs`），脚本的 72 小时窗口也按提交者时间算，不用作者日期。rebase 和 squash 合并会把提交者日期改成接近进入主线的时间，复盘关心的正是出错代码落地的时间；作者日期可能是几天前在分支上第一次写下的时间，跨 amend 和 rebase 都保持不变。
- 非返工教训也按承担问题的提交日期去重；同一条教训的同一提交被多处发现，不重复累计。
- 不要从提交说明推断对错。说明写的和代码做的不一致时，以代码为准，这种不一致本身也可能是一条教训。

## `LESSONS.md` 模板

用仓库现有文档的语言写（`AGENTS.md` 是英文就写英文），下面的中文只是示例。

```markdown
<!-- reviewed-through: <短哈希> (<yyyy-mm-dd HH:MM +时区>) -->
# 已合并改动的教训

本仓库的代码大量由 Agent 编写和合并。每次复盘检查新提交里哪些需要返工、哪些不该合并、哪些验证做得太薄，结论记在这里。改代码前先读。每条教训的格式是：一条规则、为什么、证据。“出现”按出错提交的日期去重，不按修复日或发现日；累计出现 3 天的教训移入[代码规范](docs/code-standards.md)。

<每期一段摘要：范围、提交数、返工候选数、已读及未读数、返工/正常/存疑数；另列合并把关或验证问题，以及升级与未查线索。每个已读候选一行：哈希、分类、一句话理由；存疑注明证据缺口。新的追加在后面。>

## <主题，例如：复现报告者的场景>

**<规则，一句话，祈使句。>**
<为什么：这条规则防止的是什么错误。一两句。>
- `<哈希>`（#<编号>）<错在哪、后果及证据；如已修复，附修复哈希和间隔，否则写修复未知>。
- 做对的例子：`<哈希>` <做对了什么>。
- 出现：<N> 天（<yyyy-mm-dd>, <yyyy-mm-dd>）。

## 已移入规范

这些教训出现了 3 天以上，规则和证据已经移到[代码规范](docs/code-standards.md)，评审时逐条检查。

- **<规则>**（<日期>, <日期>, <日期>）。
```

还没有代码规范文件时，开头那段把链接换成“出现 3 天的教训移入代码规范（第一次升级时新建）”，“已移入规范”一节写“暂无”。不要留指向不存在文件的链接。

## `AGENTS.md` 入口

在 `AGENTS.md` 里每次会话都要读的规则区（通常是开头几节）加一行，不要放到文件末尾的维护说明里。用 `AGENTS.md` 本身的语言：

```markdown
改代码前先读 [LESSONS.md](LESSONS.md)，照着和任务相关的教训做。
```

## 代码规范文件

仓库没有代码规范文件时，第一次升级教训时新建 `docs/code-standards.md`，用表格写，一行一条规则，第二列写评审者检查什么：

```markdown
# 代码规范

这些规则来自复盘中反复出现的问题。评审逐条检查，不满足的在评审意见里点名是哪一条。

| 规则 | 评审检查什么 |
| --- | --- |
| <规则> | <具体检查动作，附一两个代表性证据哈希> |
```

并在 `AGENTS.md` 里加一行：写代码和评审都对照这份规范。

规范只在两种情况下移出一条规则，并在本期摘要里写明理由和证据：

- 它约束的代码或子系统已经删除，附删除提交；
- 已有 lint、测试或 CI 检查自动拦住同类错误，附检查所在位置，并确认它在 CI 里实际运行。

一段时间没再出现不是移出理由，那可能正说明规则在起作用。移出后在 `LESSONS.md` 的“已移入规范”一节，给那一行补上移出日期和原因。
