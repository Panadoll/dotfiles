# 复盘与教训记录

复盘记录“最近的改动哪里做错了，用什么规则本可以拦住”。结果写在仓库根目录的 `LESSONS.md`，会话入口要求改代码前先读它。

Agent 提交频繁的仓库最需要复盘：同样的错误会在不同会话里反复出现，而每个会话都不记得上一次。

## 什么时候做

- 定期做，按提交量定节奏：一天几十个提交就每天一次，少的每周一次。
- 一次大返工、一次回滚或一次线上问题之后，不等周期，马上做一次。

一次复盘筛选 `reviewed-through` 之后的提交，同时复核上期摘要里的未读和存疑项；同一个修复提交不要重复计数。标记只记录筛选进度，不表示候选已读或结论已定。

## 修改范围

只改 `LESSONS.md`、代码规范文件（默认 `docs/code-standards.md`，已有同类文件就沿用）和会话入口（优先已有 `AGENTS.md`，其次 `CLAUDE.md`，都没有才新建 `AGENTS.md`）。为让新建的 `LESSONS.md` 通过仓库已有文档检查，可在文档清单、导航索引做最小登记；登记之外的配套改动仍禁止，看不明白登记方式就停下来报告。子系统参考页只写代码当前保证的行为，由维护流程负责，复盘不改。复盘期间不改产品代码：发现未修的 bug，报告给用户或开 issue。

## 步骤

1. **定范围。** 读 `LESSONS.md` 第一行的 `reviewed-through`，把上期未读和存疑一起作为必查输入：未读按第 4 步读完、存疑判定为返工或正常后，才从对应队列移除，其余继续带到下期。没有这个文件就是第一次复盘，按下面模板新建；用户没指定范围时用 `--last 50`，指定周期时用 `--since <周期起点前一个提交>`。之后从上期标记继续筛选。
2. **找返工候选。** 运行（Windows 上把 `python3` 换成 `python`）：

   ```bash
   python3 <技能目录>/scripts/rework.py --root <仓库根> --since <reviewed-through>   # 之后每次
   python3 <技能目录>/scripts/rework.py --root <仓库根> --last 50                     # 首次，未指定范围
   python3 <技能目录>/scripts/rework.py --root <仓库根> --since <周期起点前一个提交> # 指定周期
   ```

   脚本追溯每个提交改写的行；`--min-lines`（默认 3）按该提交改写的近期行总数算，跨来源累加。另列标题带 revert / 回滚 / 撤销 关键词的提交，这是启发式，不证明真的回滚；已在返工候选里的只加 `[回滚]`，不重复列出。常见锁文件不计数（含 `bun.lock`、`bun.lockb`、`poetry.lock`、`Pipfile.lock`、`composer.lock`、`Gemfile.lock`）；非测试和测试分开计数，非测试含注释、配置，不代表语义代码行。默认不算文档，`--include-docs` 时文档单列，不混入前两类。修复类只按标题识别并排在前面，同类按非测试行数排序；版本号式标题的仓库，排序参考价值低。只命中近期测试行不等于整个提交只改测试。移动或重命名沿旧路径，只算真正改写的行。

   范围超过 `--max-commits`（默认 400）、浅克隆或任何 git 调用失败时，脚本拒绝推进标记。超限就调大上限重跑，不跳过较早提交；浅克隆先 `git fetch --unshallow`。`--head <commit>` 默认 `HEAD`；`--last N` 从 head 往回数，`--since X` 表示 `X..head`，标记记录解析后的 head，下一期不会重扫已合并的分支。

   保存首扫命令和本期标记；复核或验证时在原命令上加 `--head <本期标记>`，保留原 `--last` 或 `--since` 起点及筛选参数（如 `--head <本期标记> --last 50`），避免复盘提交让窗口滑动。不要用重跑得到的新 head 覆盖本期标记。

   用合并提交（merge commit）合并 PR 的仓库，分支上的分步提交也在范围里，PR 内部的迭代会成为候选，按下面“明确分步”的标准判断，不要直接算返工。
3. **再找脚本看不到的线索。** 72 小时是候选窗口，不是归因截止；略超窗口的修复也要补查。先看 diff 是否为空或只改文档，再展开提交正文，例如 `git log --format='%h %s%n%b' <本期起点前一个提交>..<本期标记>`；squash 正文里复制来的旧修复说明，不算本提交又修了一次。还要看：
   - 提交说明或 PR 里写着“又”“再次”“漏了”“follow-up”的；
   - 重新打开的 issue、同一个 issue 被多个提交引用的；
   - 超出已确认范围、违反既定决策、合并检查未通过或验证声明缺少证据的；
   - 同一天里对同一功能的多次发布；
   - 脚本看不到的纯添加补漏（缺失的文件、清单、依赖）、1–2 行关键配置修正、恢复误删，靠人工线索补入。

   本期候选 = 脚本输出 ∪ 本步人工线索 ∪ 上期未读和存疑，按修复提交哈希去重；脚本的独立回滚列表也算候选。每个候选只给一个主分类，多来源不重复计数。

   查 CI 时，绑定实际被合并版本的 PR head SHA，以 `mergedAt` 为界核对当时要求的检查：只把合并前已完成且通过的检查算作已验证，后来的绿色重跑不能倒推合并时已通过。取消或未完成不算通过，但是否违反合并要求仍要核对当时约定；查不到记录就写证据不足。

   没有远程权限、查不了 issue 和 CI 时，只用 git 历史做，并在本期摘要里写明“未查 issue 和 CI”。
4. **逐条判断。** 按脚本顺序和人工线索强弱读，不要求一期读完；停下时剩余候选列为未读。返工候选要读前后提交的 diff 和当时的范围说明；只有证据能连成这条链才算返工：原提交当时应满足什么行为 → 它引入或在声称修复时遗漏了什么缺陷 → 后续提交如何修正同一个缺陷。`git blame` 只说明谁最近写过这些行，不证明谁引入了缺陷。

   “当时应满足什么”可用出错提交当时已有的文档、规范、测试，代码已支持的平台、拓扑或输入（如已有对应分支、解析器已接受），以及 issue/PR 的验收要求作证；后来才扩大的承诺不能倒推。承诺覆盖多大范围也以项目当时的声明为准：文档、规范或 CI 写明对所有入口成立的，后加的入口也要满足；只在某条路径上实现过、没有项目级声明的，不能推定其他入口也有这个承诺，证据不足就列为存疑。隐含要求（如不阻塞 UI 线程、不丢数据）只有在当时的文档、架构约束或既有同类实现里找到依据才采信，否则存疑。

   脚本命中的只是最近改写者；命中只是重排、注释或测试时，用 `git log -S <字符串> -- <路径>` 或 `git log -L :<符号>:<路径>` 沿历史追到首个实现，再用 `git show <sha>:<路径>` 核对当时的代码。追不到原始引入就列为存疑。判返工时写出三个角色及哈希：最早的错误行为（出错日期按它）、使之暴露的变化（没有则写无）、修复提交，不把暴露变化自动当成引入点。同一个缺陷按错误机制认定，不按症状：后果变了（如从静默出错变成报错拒绝），仍追到最早出现同一错误机制的提交。

   明确分步且没有破坏当时约定的行为、支持新增调用方、重构或格式化，都不算返工；没有写分步计划也不自动算错。提交说明写了“不在本次范围”不能单独免责，要看代码是否新破坏了已支持的行为。后续提交叫 `fix`、提到“补齐”，或很快改写同一文件，都只是线索。证据不能区分缺陷与范围扩展时，列为“存疑”，写明哈希和缺什么证据，不计入教训；也不要直接归为正常。

   “挑几条”按去重后的候选提交计，一个提交下面列了几个被改写的提交也只算一条。

   “已读”按结论定范围：判返工，读完构成证据链所需的 diff 即可；混合提交确认一条完整返工链就能判返工，其余部分在理由里写“其余未审”。判正常，要读完全部非生成文件的 diff，锁文件、生成文件、批量翻译可声明跳过。只读一部分且返工、正常都判不了的算未读，不混入存疑；读完全部非生成文件（可按上述例外声明跳过）仍缺判定证据的，才列存疑。

   混合提交只要有一条完整返工链，主分类就是返工，新增功能部分在理由里说明；全部疑点都不成立才算正常。一次返工指一个修复提交加上它修的那个（或那几个）提交，无论改写几个早先的提交，仍只计一次。

   合并把关失误、验证不足即使没有后续修复，也能形成教训，但要指出违反了哪项已确认的范围、决策或验证要求，并附对应提交与事实证据。没有新增自动测试不等于验证不足；没有运行记录只能证明记录缺失，不能推断从未验证。这类问题单列，不计入返工次数；无法确认就存疑。

   测试或夹具本身有缺陷、并有后续修复链的，按返工计一次，不再另计一次验证不足；只有另有被违反的已确认要求时，验证不足才单独成条。
5. **归纳成规则。** 把已确认的问题按“如果当时遵守哪条规则就不会出错”归类。规则写的是一类错误，换一个功能也用得上；具体的文件、函数、功能名放进证据里，不写进规则：

   | 不好：只是重述这次事故 | 好：一类错误的规则 |
   | --- | --- |
   | 改 `update.sh` 时要重启所有工作进程 | 判断运行中的进程要不要重启，不能只看它读的文件有没有变；启动时加载的配置和开关，文件 diff 里看不出来 |
   | `--intent` 要写清自洽性 | 拆分一个字段的职责时，同一个改动里写清新字段必须独立成立的条件，不能留到下一个 PR |

   规则要能照着检查，例如“修一处时搜一遍同样写法的兄弟代码，一起修”，而不是“更仔细一点”。
   - 已有的教训又出现了：共同失效机制和检查动作一致才合并证据、更新天数；只是主题相近的不合并凑天数。
   - 新的：按模板新增一条。
   - 只关乎某个子系统的规则（例如“这个缓存键必须带租户 ID”），也写进 `LESSONS.md`，在主题里注明子系统，不改参考页。如果代码或测试已经保证了这条约束、参考页却没写，在汇报里指出，留给下次改这个子系统或巡检时补进参考页。
6. **也记做对了的。** 有提交明显做对了（复现了报告者的原始场景、一次修全了所有同类、写清了手动破坏过什么），在对应教训下记一行“做对的例子”。这比只记错误更能教会下一个 Agent 该怎么做。
7. **升级。** 一条教训累计出现 3 天（可跨多次复盘）时，先写出几次事故共同的失效机制和共同检查动作，成立才移进代码规范。规范保留代表性叙述及完整“出错日期 → 出错提交 → 修复提交”台账；非返工且无修复的写“修复未知”。`LESSONS.md` 挪到“已移入规范”，一行保留日期和哈希，不只留日期。评审从此逐条检查。

   `LESSONS.md` 每次会话都要读，无论是否升级，重复事故只保留最有代表性的叙述，其余证据压成日期和哈希；不得丢失累计日期的依据或未解决的未读、存疑项。旧摘要也压缩叙述，不重复展开教训正文。
8. **写本期摘要，推进标记。** 在标题下、第一个主题之前追加一段，不加单独标题：本期范围和提交数、脚本候选数（注明参数）、去重后的候选总数、已读及未读数、返工/正常/存疑数、主要问题、升级与未查线索；合并把关或验证问题另列，不混入返工数。每个已读候选一行：哈希、来源（脚本 / 人工，可兼有）、主分类、一句话理由；存疑附证据缺口。未读候选逐个列哈希，和存疑一起留给下期必查。摘要数应与条目相符，返工比例不是质量目标。脚本成功且摘要写完后，才替换第一行标记。
9. **提交。** 只提交上面修改范围内的文件，单独一个提交。本期没有新证据时，只推进 `reviewed-through`，摘要里写“本期无新教训”。

## 证据要求

- 每条证据都要有提交哈希，必要时附 issue 或 PR 编号。写之前用 `git show <哈希>` 确认它确实是你说的那样。
- 写清错在哪和可核对的后果；返工还要写后来怎么修、隔了多久。“`<哈希A>` 只修了一个调用方，`<哈希B>` 两天后补上另外三个”，而不是“修得不完整”。没有修复记录就写未知，不编造。
- “出现”按出错提交的日期去重，不按修复日或发现日。9 月 3 日的 B 修了 9 月 1 日的 A，就记 9 月 1 日（`git show -s --format=%cs <A>`）。同一个修复对同一条规则只记一天；同一缺陷涉及多个出错提交时，取已证实最早引入它的提交日期。后来声称修复却漏掉已支持情形的，是另一次失误，按漏修提交的日期单独计，可以归入不同的教训；返工次数仍按修复提交只计一次。无法确定就存疑，不猜日期。同一天的多次返工只算一天，但都可以列为证据。
- 日期一律取提交者日期（`%cs`），脚本的 72 小时窗口也按提交者时间算，不用作者日期。rebase 和 squash 合并会把提交者日期改成接近进入主线的时间，复盘关心的正是出错代码落地的时间；作者日期可能是几天前在分支上第一次写下的时间，跨 amend 和 rebase 都保持不变。
- 非返工教训也按承担问题的提交日期去重；同一条教训的同一提交被多处发现，不重复累计。
- 不要从提交说明推断对错。说明写的和代码做的不一致时，以代码为准，这种不一致本身也可能是一条教训。

## `LESSONS.md` 模板

没有更高优先级的语言要求时，用仓库现有文档的语言，下面的中文只是示例。

```markdown
<!-- reviewed-through: <短哈希> (<yyyy-mm-dd HH:MM +时区>) -->
# 已合并改动的教训

本仓库的代码大量由 Agent 编写和合并。每次复盘检查新提交里哪些需要返工、哪些不该合并、哪些验证做得太薄，结论记在这里。改代码前先读。每条教训写规则、为什么和证据。“出现”按出错提交的日期去重，不按修复日或发现日；共同失效机制和检查动作一致、累计出现 3 天的教训移入[代码规范](docs/code-standards.md)。

<每期一段摘要：范围、提交数、脚本候选数（注明参数）、去重后的候选总数（含上期未读和存疑）、已读及未读数、返工/正常/存疑数；另列合并把关或验证问题，以及升级与未查线索。每个已读候选一行：哈希、来源（脚本 / 人工，可兼有）、一个主分类、一句话理由；存疑注明证据缺口。未读逐个列哈希，和存疑一起作为下期必查输入，读完或判定后才从对应队列移除。新的摘要追加在后面。>

## <主题，例如：复现报告者的场景>

**<规则，一句话，祈使句。>**
<为什么：共同失效机制，以及能拦住它的共同检查动作。一两句。>
- `<哈希>`（#<编号>）<错在哪、后果及证据；如已修复，附修复哈希和间隔，否则写修复未知>。
- 做对的例子：`<哈希>` <做对了什么>。
- 出现：<N> 天（<出错日期> → `<出错哈希>` → `<修复哈希或未知>`；各日均保留）。

## 已移入规范

这些教训累计出现至少 3 天，已确认共同机制和检查动作；规则及完整台账已移到[代码规范](docs/code-standards.md)，评审时逐条检查。

- **<规则>**（<出错日期> → `<出错哈希>` → `<修复哈希或未知>`；各日均保留）。
```

还没有代码规范文件时，开头那段把链接换成“出现 3 天的教训移入代码规范（第一次升级时新建）”，“已移入规范”一节写“暂无”。不要留指向不存在文件的链接。

## 会话入口

仓库已有 `AGENTS.md` 就写进它；只有 `CLAUDE.md` 就写进 `CLAUDE.md`；都没有才新建 `AGENTS.md`。在选定文件每次会话都要读的规则区（通常在开头）加一行，不放到末尾维护说明里。没有更高优先级的语言要求时，沿用仓库现有文档的语言：

```markdown
改代码前先读 [LESSONS.md](LESSONS.md)，照着和任务相关的教训做。
```

## 代码规范文件

仓库没有代码规范文件时，第一次升级教训时新建 `docs/code-standards.md`，用表格写，一行一条规则，第二列写评审者检查什么：

```markdown
# 代码规范

这些规则来自复盘中反复出现的问题。评审逐条检查，不满足的在评审意见里点名是哪一条。

| 规则 | 评审检查什么 | 出现台账 |
| --- | --- | --- |
| <规则及共同失效机制> | <共同的具体检查动作> | <出错日期> → `<出错哈希>` → `<修复哈希或未知>`；各日均保留 |
```

并在上述选定的入口文件里加一行：写代码和评审都对照这份规范。

规范只在两种情况下移出一条规则，并在本期摘要里写明理由和证据：

- 它约束的代码或子系统已经删除，附删除提交；
- 已有 lint、测试或 CI 检查自动拦住同类错误，附检查所在位置，并确认它在 CI 里实际运行。

一段时间没再出现不是移出理由，那可能正说明规则在起作用。移出后在 `LESSONS.md` 的“已移入规范”一节，给那一行补上移出日期和原因。
