# 复盘与教训记录

Agent 提交频繁的仓库，同样的错误会在不同会话里反复出现，而每个会话都不记得上一次。复盘检查已合并的提交里哪些是返工、哪些不该合并、哪些验证做得太薄，把教训写成下一位 Agent 改代码前会读的 `LESSONS.md`。定期做，按提交量定节奏；一次大返工、一次回滚或一次线上问题之后，不等周期，马上做一次。

## 修改范围

只改 `LESSONS.md`、代码规范文件和 `AGENTS.md` 入口。子系统参考页只写代码当前保证的行为，由维护它的流程负责，复盘不改。复盘期间不改产品代码：发现还没修的 bug，报告给用户或开 issue。

## 检查脚本

`scripts/rework.py`（相对本技能目录，只依赖 Python 3.9+ 标准库和 git）只读：对范围内每个非合并提交用 `git blame` 追溯它改写的行，列出改写了几天内刚写成代码的提交和回滚提交，作为返工候选。支持中文、空格等路径，移动文件不算改写；候选不是缺陷归因。范围超限、浅克隆或任何 git 调用失败时报错，不会跳过历史再推进标记；标记记的是扫描时的 HEAD。

## 工作流

按 [references/lessons.md](references/lessons.md) 执行：

1. 从 `LESSONS.md` 第一行的 `reviewed-through` 定范围；没有这个文件就是第一次复盘，取最近 50 个提交或最近一周，取少的那个。
2. 用 `rework.py` 找返工候选，再补查 issue、改动范围和合并时的 CI 证据，并复核上期存疑项。
3. 读前后提交的 diff，证据能连成“当时应满足什么行为 → 引入或遗漏了什么缺陷 → 后续怎么修的”才算返工；明确分步、支持新增调用方、重构和格式化都不算，证据不足列为存疑。合并把关失误和验证不足单列，不计入返工数。
4. 把证据归纳成一类错误的规则，写进 `LESSONS.md`，每条附提交哈希，按出错提交的日期计“出现”天数，不按修复日；做对的例子也记。只关乎一个子系统的规则也写进 `LESSONS.md`，在主题里注明子系统。
5. 累计出现 3 天的教训移进代码规范，评审从此逐条检查。规范里的规则只在约束对象已删除，或已有自动检查拦住同类错误时移出。
6. 写紧凑的本期摘要（含存疑项），推进 `reviewed-through`，只提交修改范围内的文件。

## 写作要求

- 教训写的是一类错误，具体文件、函数、功能名放在证据里，不写进规则。
- 每条证据写之前用 `git show` 核实；日期、哈希、计数要能互相核对。
- `LESSONS.md` 用仓库现有文档的语言写。
- 返工比例不是质量目标，不要为了凑数或好看调整判定。
