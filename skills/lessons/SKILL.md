# 复盘与教训记录

Agent 提交频繁的仓库，同样的错误会在不同会话里反复出现，而每个会话都不记得上一次。复盘检查已合并的提交里哪些是返工、哪些不该合并、哪些验证做得太薄，把教训写成下一位 Agent 改代码前会读的 `LESSONS.md`。定期做，按提交量定节奏；一次大返工、一次回滚或一次线上问题之后，不等周期，马上做一次。

## 修改范围

只改 `LESSONS.md`、代码规范文件和 `AGENTS.md` 入口；可为新建 `LESSONS.md` 通过已有文档检查做最小登记，方式不明就停下报告。登记之外的配套改动仍禁止，子系统参考页仍由维护流程负责，复盘不改。期间不改产品代码：发现未修的 bug，报告给用户或开 issue。

## 检查脚本

`scripts/rework.py`（相对本技能目录，只依赖 Python 3.9+ 标准库和 git）只读：用 `git blame` 追溯每个非合并提交改写的近期行，另列标题带 revert / 回滚等关键词的提交。关键词只是启发式，重叠项只标 `[回滚]`；候选不是缺陷归因。支持中文、空格等路径，移动文件不算改写。范围超限、浅克隆或任何 git 调用失败时报错，不推进标记；标记记录 `--head` 解析后的提交（默认 `HEAD`）。

## 工作流

按 [references/lessons.md](references/lessons.md) 执行：

1. 从 `LESSONS.md` 第一行的 `reviewed-through` 定范围；首次未指定范围时用 `--last 50`，用户指定周期时用 `--since <周期起点前一个提交>`。
2. 用 `rework.py` 找候选，再补查人工线索和上期存疑项；本期候选取脚本与人工线索的并集，按修复提交哈希去重，每个只给一个主分类。72 小时只是候选窗口，不是归因截止。
3. 读前后 diff，证据能连成“当时应满足什么行为 → 原始引入或遗漏的缺陷 → 后续修复”才算返工；明确分步、新增调用方、重构和格式化都不算，证据不足列为存疑。测试或夹具缺陷有修复链也按返工计一次；合并把关或验证不足只在另有被违反的已确认要求时单列，不重复计数。
4. 把证据归纳成一类错误的规则，写进 `LESSONS.md`，每条附提交哈希，按出错提交的日期计“出现”天数，不按修复日；做对的例子也记。只关乎一个子系统的规则也写进 `LESSONS.md`，在主题里注明子系统。
5. 共同失效机制和检查动作一致、累计出现 3 天的教训移进代码规范，保留各日哈希台账，评审逐条检查；只因主题相近不合并。规则只在约束对象已删除，或已有自动检查拦住同类错误时移出。
6. 摘要分别写脚本候选数和去重总数（含存疑项），写完才推进标记。复核沿用原参数并加 `--head <本期标记>`，不用重跑的新 head 覆盖；只提交修改范围内的文件。

## 写作要求

- 教训写的是一类错误，具体文件、函数、功能名放在证据里，不写进规则。
- 每条证据写之前用 `git show` 核实；日期、哈希、计数要能互相核对。
- 没有更高优先级的语言要求时，用仓库现有文档的语言。
- 返工比例不是质量目标，不要为了凑数或好看调整判定。
