# Subsystem 维护与审计操作指南 (Maintenance Guide)

> 本指南规范了子系统的生命周期管理、日常巡检以及 PR Review 审计标准。

---

## 一、核心维护铁律 (Core Commandments)

1. **`Code_t ↔ Docs_t` 同 PR 提交**
   * 任何代码变更，只要影响了子系统的**对外契约、事实源符号、状态流转、运行时路径或降级策略**，必须在**同一个 PR / 提交**中同步更新对应的 `docs/subsystems/<name>.md`。
   * 纯内部性能优化或不改变对外契约的重构，无需修改文档。

2. **符号链接原则（禁止粘贴易变实现）**
   * 文档中只能使用文件名、类名、接口名和函数名链接；
   * 严禁在子系统文档中粘贴大段易变的函数体代码。

3. **契约防降级原则（严禁改弱不变量）**
   * 当测试或代码变更导致子系统的 `Invariants（核心不变量）` 报错时，**严禁 Agent 直接把文档里的 Invariants 改弱或删掉来强行蒙混通过**！
   * 必须在以下两者间做出严谨判定：
     - 这是破坏契约的代码退化（Architecture Regression） $\rightarrow$ 坚决阻断改动，修复代码；
     - 这是经过正式评估的架构演进 $\rightarrow$ 需在 PR 描述中给出充分依据。

---

## 二、PR Review 审计清单 (PR Review Checklist)

当审查一个涉及子系统的 PR 或在提交前做自检时，依次执行以下 4 步：

```markdown
- [ ] 1. 定位受影响的子系统：本次代码改动涉及了哪个/哪几个子系统切片？
- [ ] 2. 检查事实源链接：文档中声明的类/函数/符号，是否依然存在且路径正确？
- [ ] 3. 检查语义变更自述：PR 描述是否清晰说明了 Before/After 的行为变化？
- [ ] 4. 运行验证命令：实际运行文档中第 6 节声明的 `Verification` 命令，确认 100% 通过。
```

---

## 三、三权分立分诊模型 (Triage Model)

当在巡检或审计中发现“代码与文档不一致”时，严格按照以下三类进行归因分诊：

| 分诊类别 | 判定标准 | 处理动作 |
| :--- | :--- | :--- |
| **Doc Drift (文档漂移)** | 代码功能是预期内的升级，但文档记录落后了 | 在当前分支中同步更新子系统文档与事实源表格 |
| **Verification Gap (校验缺陷)** | 代码功能完备，但文档中给出的测试/验证命令失效了 | 修正文档中的 Verification 命令，重新执行确保绿灯 |
| **Architecture Regression (架构退化)** | 代码改动违反了子系统的不变量或设计规范（如引入循环依赖、绕过状态校验） | **立即中止并阻断改动！** 勒令修改代码，保护架构底线 |
