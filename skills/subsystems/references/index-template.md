# 子系统参考

这些页面描述当前的职责、运行时路径、状态和约束。先读与任务相关的那一页，再沿链接核对要改的实现。

| 子系统 | 参考 |

一个子系统可以跨多个包或仓库。参考页描述这些部分共同提供的行为，不需要列出每个函数。

## 维护参考

当改动影响已记录的职责、接口、状态转换、运行时路径、兼容规则或失败行为时，在同一个 PR 里更新对应参考。不改变这些契约的内部重构不需要改文档。

一个事实只放在一页，其他地方链接过去。链接到源文件和具名符号，不要复制会变的实现。签名看不出的字段含义和约束要写清楚。

新建参考时，写清职责与边界、事实源、主要运行时路径、状态转换、重要约束和现有验证命令，相关时补上失败和兼容行为。只写当前行为，提议放在 issue 或 PR 里。

改完后运行 `python <subsystems 技能目录>/scripts/check_refs.py`，并把页首的 `verified-at` 更新为核对时的提交。

## 描述 PR 的语义变更

对每个受影响的子系统，写清可观察到的变化：什么条件触发，改动前怎样，改动后怎样。相关时写上接口、状态、兼容和失败行为的变化。链接受影响的参考、实现和验证证据。重构没有改变已记录的行为时，明确说出来。

这是作者给出的说明，由评审对照 diff 和周边代码核实，不是自动证明的兼容性结论。

## 评审改动

1. 找出受影响的子系统和实际运行路径。
2. 对照改动前后的实现核实所说的行为变化，追踪改动行之外的调用方和状态转换。
3. 检查改变的契约是否写进了对应参考，源码链接是否仍然有效。
4. 检查引用的测试或运行证据是否真的覆盖了所说的行为，并报告没有运行的检查。

只更新文档证明不了实现正确。行为变化仍然需要测试或运行证据。
