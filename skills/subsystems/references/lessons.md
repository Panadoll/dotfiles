# 复盘与教训记录

子系统参考记录代码“现在是什么样”，复盘记录“最近的改动哪里做错了，用什么规则本可以拦住”。结果写在仓库根目录的 `LESSONS.md`，`AGENTS.md` 要求改代码前先读它。

Agent 提交频繁的仓库最需要复盘：同样的错误会在不同会话里反复出现，而每个会话都不记得上一次。

## 什么时候做

- 定期做，按提交量定节奏：一天几十个提交就每天一次，少的每周一次。
- 一次大返工、一次回滚或一次线上问题之后，不等周期，马上做一次。

一次复盘只看 `reviewed-through` 之后的提交，看完把它往前推。范围不要重叠，同一件事不要算两次。

## 修改范围

只改 `LESSONS.md`、代码规范文件（默认 `docs/code-standards.md`，仓库已有同类文件就沿用）、子系统参考的“约束与失败行为”小节，以及 `AGENTS.md` 的入口。复盘期间不改产品代码：发现还没修的 bug，报告给用户或开 issue。

## 步骤

1. **定范围。** 读 `LESSONS.md` 第一行的 `reviewed-through`。没有这个文件就是第一次复盘：范围取最近一个周期，用户指定了就按用户的；没指定时取最近 50 个提交，或最近一周，取少的那个。然后按下面的模板新建文件。
2. **找返工候选。** 运行（Windows 上把 `python3` 换成 `python`）：

   ```bash
   python3 <技能目录>/scripts/rework.py --root <仓库根> --since <reviewed-through>   # 之后每次
   python3 <技能目录>/scripts/rework.py --root <仓库根> --last 50                     # 第一次
   ```

   脚本对每个提交追溯它改写的行是哪个提交写的，列出改写了 72 小时内刚写成代码的提交，以及回滚提交。每个提交只出现一次，下面列出它改写了哪些提交的多少行，产品代码和测试分开计数。修复类提交排在前面；只改写了测试行的，多半是测试脚手架跟着调整，不是产品返工。默认不算文档文件，`--include-docs` 可以加上。
3. **再找脚本看不到的线索。** 脚本只看行级改写。还要看：
   - 提交说明或 PR 里写着“又”“再次”“漏了”“follow-up”的；
   - 重新打开的 issue、同一个 issue 被多个提交引用的；
   - 合并时测试是红的、或者 PR 没写跑了什么的；
   - 同一天里对同一功能的多次发布。

   没有远程权限、查不了 issue 和 CI 时，只用 git 历史做，并在本期摘要里写明“未查 issue 和 CI”。
4. **逐条判断。** 从候选里挑信号最强的先读，不必读完所有候选，但要在摘要里写明读了几条。对每个候选读两边的 diff，回答：前一个提交错在哪？这是一次正常的连续开发（先做骨架再补细节、按计划分步提交、给新的调用方补对称的支持），还是本该一次做对？只有后者算一次返工。重构和格式化也不算。前一个提交的说明或 PR 里明确写了“这部分留到下一步”的，算分步；后一个提交事后才说“补上另一半”的，算返工。拿不准就不算，在摘要里列为“存疑”。

   “挑几条”按脚本输出里的提交计，一个提交下面列了几个被改写的提交也只算一条。

   一次返工指一个修复提交加上它修的那个（或那几个）提交。同一个修复提交改写了几个早先的提交，仍然只算一次。
5. **归纳成规则。** 把返工按“如果当时遵守哪条规则就不会出错”归类。规则写的是一类错误，换一个功能也用得上；具体的文件、函数、功能名放进证据里，不写进规则：

   | 不好：只是重述这次事故 | 好：一类错误的规则 |
   | --- | --- |
   | 改 `fm-update.sh` 时要重启所有 second mate | 判断运行中的进程要不要重启，不能只看它读的文件有没有变；启动时加载的配置和开关，文件 diff 里看不出来 |
   | `--intent` 要写清自洽性 | 拆分一个字段的职责时，同一个改动里写清新字段必须独立成立的条件，不能留到下一个 PR |

   规则要能照着检查，例如“修一处时搜一遍同样写法的兄弟代码，一起修”，而不是“更仔细一点”。
   - 已有的教训又出现了：在那条下面补证据，更新次数。
   - 新的：按模板新增一条。
   - 只关乎某个子系统的规则（例如“这个缓存键必须带租户 ID”），写进该子系统参考的“约束与失败行为”，`LESSONS.md` 里留一行链接。仓库还没有子系统参考时，先写进 `LESSONS.md`，并在汇报里建议为这个子系统建参考页。
6. **也记做对了的。** 有提交明显做对了（复现了报告者的原始场景、一次修全了所有同类、写清了手动破坏过什么），在对应教训下记一行“做对的例子”。这比只记错误更能教会下一个 Agent 该怎么做。
7. **升级。** 一条教训累计出现 3 天（可以跨多次复盘累计），就把规则移进代码规范，带上最有代表性的证据。`LESSONS.md` 里把它挪到“已移入规范”一节，只留一行和日期。评审照代码规范检查，所以升级之后这条规则在每次评审里都会被检查。
8. **写本期摘要，推进标记。** 在标题下、第一个主题之前的摘要区追加一段，不加单独的标题：本期范围和提交数、脚本给出几个候选、读了几条、判定几次返工、主要错在哪一类、哪些教训升级了、哪些线索没查。把第一行替换成脚本最后打印的那一行，它是范围内最后一个提交和它的提交时间。
9. **提交。** 只提交上面修改范围内的文件，单独一个提交。本期没有新证据时，只推进 `reviewed-through`，摘要里写“本期无新教训”。

## 证据要求

- 每条证据都要有提交哈希，必要时附 issue 或 PR 编号。写之前用 `git show <哈希>` 确认它确实是你说的那样。
- 写清楚错在哪、后来怎么修的、隔了多久。“`<哈希A>` 只修了截图里那个 agent，`<哈希B>` 两天后补上另外三个”，而不是“修得不完整”。
- “出现”按出错提交的日期计不同的日子。出错提交是被返工的那个，不是修复它的那个：9 月 3 日的提交 B 修了 9 月 1 日的提交 A，就记 9 月 1 日（`git show -s --format=%cs <A>`）。一次返工只算一天，不管修复是哪天做的；同一天的多次返工也只算一天，但都可以列为证据。
- 不要从提交说明推断对错。说明写的和代码做的不一致时，以代码为准，这种不一致本身也可能是一条教训。

## `LESSONS.md` 模板

用仓库现有文档的语言写（`AGENTS.md` 是英文就写英文），下面的中文只是示例。

```markdown
<!-- reviewed-through: <短哈希> (<yyyy-mm-dd HH:MM +时区>) -->
# 已合并改动的教训

本仓库的代码大量由 Agent 编写和合并。每次复盘检查新提交里哪些需要返工、哪些不该合并、哪些验证做得太薄，结论记在这里。改代码前先读。每条教训的格式是：一条规则、为什么、证据。“出现”记录在多少个不同的日子发现过它；出现 3 天的教训移入[代码规范](docs/code-standards.md)。

<每期一段摘要：时间范围、提交数、返工数、主要问题、升级了哪些教训。新的追加在后面。>

## <主题，例如：复现报告者的场景>

**<规则，一句话，祈使句。>**
<为什么：这条规则防止的是什么错误。一两句。>
- `<哈希>`（#<编号>）<错在哪>，`<哈希>` <怎么修的、隔了多久>。
- 做对的例子：`<哈希>` <做对了什么>。
- 出现：<N> 天（<yyyy-mm-dd>, <yyyy-mm-dd>）。

## 已移入规范

这些教训出现了 3 天以上，规则和证据已经移到[代码规范](docs/code-standards.md)，评审时逐条检查。

- **<规则>**（<日期>, <日期>, <日期>）。
```

还没有代码规范文件时，开头那段把链接换成“出现 3 天的教训移入代码规范（第一次升级时新建）”，“已移入规范”一节写“暂无”。不要留指向不存在文件的链接。

## `AGENTS.md` 入口

在 `AGENTS.md` 里每次会话都要读的规则区（通常是开头几节）加一行，不要放到文件末尾的维护说明里。用 `AGENTS.md` 本身的语言：

```markdown
改代码前先读 [LESSONS.md](LESSONS.md)，照着和任务相关的教训做。
```

## 代码规范文件

仓库没有代码规范文件时，第一次升级教训时新建 `docs/code-standards.md`，用表格写，一行一条规则，第二列写评审者检查什么：

```markdown
# 代码规范

这些规则来自复盘中反复出现的问题。评审逐条检查，不满足的在评审意见里点名是哪一条。

| 规则 | 评审检查什么 |
| --- | --- |
| <规则> | <具体检查动作，附一两个代表性证据哈希> |
```

并在 `AGENTS.md` 里加一行：写代码和评审都对照这份规范。
