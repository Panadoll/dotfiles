# 子系统参考文档

大仓库的信息量远超 Agent 一次能装下的上下文。每次改动都从源码重新推一遍“谁拥有什么状态、请求怎么走、哪里不能动”，既慢又容易漏。子系统参考把这些结论压缩成一页，让下一位 Agent 先读结论，再沿链接核对源码。

这套做法来自 magpie（`docs/subsystems/` + `LESSONS.md`）、DeepSeek Harness（文档分层与 Agent Notes）和 pstack（只读体检、源码比对、交付前实测）。

## 信息放哪里

一个事实只放一处，其他地方链接过去。

| 位置 | 放什么 | 不放什么 |
| --- | --- | --- |
| 代码 | 当前行为 | 为什么这样设计 |
| 子系统参考 `docs/subsystems/<name>.md` | 职责与边界、事实源、运行时路径、状态、约束与失败行为、验证命令 | 实现细节的复制、历史经过、未来计划 |
| Agent Notes `docs/agent-notes/` | 为什么选这个方案、放弃了什么、什么条件下可以重新考虑 | 当前行为的描述 |
| 测试 | 哪些状态绝不允许出现 | — |
| `AGENTS.md` / `CLAUDE.md` | 每次会话都要遵守的一两行规则，加链接 | 长篇说明 |
| Git 历史 | 原始演变过程 | — |

仓库已有等价的东西（`ARCHITECTURE.md`、`docs/architecture/`、`.agents/notes/`、`SPEC.md`）时，沿用它的位置和名字，不要另起一套。下文的路径都是默认值。

## 检查脚本

`scripts/check_refs.py`（相对本技能目录，只依赖 Python 3 标准库和 git）只读地检查：

- 相对链接的目标和锚点是否存在；
- 绑定到文件的符号是否还在那个文件里，写法是 ``[`Sym`](path)``、`` `Sym` in [..](path) `` 或 ``[..](path) `Sym` ``；
- `验证：` 段落和 `## 验证` 章节里点名的测试，以及验证代码块里引用的测试文件，是否还能在仓库里找到；
- 索引是否列全了每一页；
- 页面里 `<!-- verified-at: <commit> -->` 之后，被引用的源文件是否改过。

```bash
python <技能目录>/scripts/check_refs.py --root <仓库根>              # 全部
python <技能目录>/scripts/check_refs.py --root <仓库根> --doc <name>  # 单页
```

失败项返回码为 1。“改过的源文件”只是提示：说明需要人工复核，不代表文档错了。

## 工作流

用户的说法对应到下面某一项即可，不需要斜杠命令。

### 建立参考（init）

1. **先盘点已有文档。** 找 `AGENTS.md`、`CLAUDE.md`、`README`、`docs/`、`SPEC.md`、架构图和已有决策记录。已有一份整体规格（例如 `SPEC.md`）时，不要删它，也不要把它整段搬进参考页：参考页写各子系统当前的契约并链接到源码，索引页链接到这份规格。如果规格和代码不一致，把不一致之处列进汇报，让用户决定是修规格还是退役它。
2. **从代码里切分子系统，不要先问用户。** 按“改动时必须一起理解的范围”来切，不按目录切。下面这些都是切分信号：拥有持久状态，有对外接口（API、CLI、事件、文件格式），有自己的失败或降级策略，跨多个包协作完成一件事。不要给工具函数、单个小模块或纯 UI 组件单独建页。小仓库通常 2 到 6 页就够；切不准时宁可少切，以后再拆。
3. **写参考页。** 按 [references/reference-template.md](references/reference-template.md) 写。每条断言都要能在源码里找到出处，写不出出处的就不写。没有证据的推测放进“未确认”小节，或者直接问用户。
4. **写索引和入口。** 按 [references/index-template.md](references/index-template.md) 写 `docs/subsystems/README.md`，并在 `AGENTS.md`（没有就新建）加两三行：改某个子系统前先读它的参考并核对链接的源码，PR 按索引页的规则更新文档。
5. **交付前实测。**
   - 跑一遍 `check_refs.py`，修到没有失败项。
   - 逐条执行每页“验证”里的命令。命令要写成从仓库根目录就能运行的形式，不要用绝对路径或本机才有的虚拟环境路径；依赖怎么装写在命令旁边。
   - 命令失败时先排查环境原因再下结论：代理变量（`HTTP_PROXY` 会拦截访问 localhost 的测试）、端口占用、缺依赖、权限。确认是环境问题后，把前置条件写进该页的“验证”小节，再重跑一次。
   - 结果按实际情况记录：通过；失败（附错误和排查结论）；需要外部条件（写清条件）；没有测试（写“暂无”，在报告里记为验证缺口）。不要编造命令，也不要为了跑通而改测试。
   - 回到源码逐条核对强断言：“总是”“从不”“无条件”“只有”“与 X 不同”。检查脚本只能证明符号存在，证明不了这些说法正确。
   - 以上都做完后，在页首写 `<!-- verified-at: <当前 HEAD 的短哈希> -->`。
6. **汇报。** 列出切分了哪几页、各页依据了哪些源码、验证结果、未确认的问题。

### 改代码前（doctor）

1. 读索引，找到对应的子系统参考。没有对应页就照常读代码，并在结束时建议补一页。
2. 跑 `check_refs.py --doc <name>`。有失败项或“改过的源文件”提示时，先按链接核对源码，以代码为准，再动手。
3. 读该子系统链接的 Agent Notes。要改动其中某个已记录的取舍时，先告诉用户。

### 提交前（audit）

1. 从 `git diff` 找出受影响的子系统，按实际运行路径找，不按改动的文件名找。
2. 判断改动是否影响了职责、接口、状态转换、运行时路径、兼容规则或失败行为。影响了就在同一个提交或 PR 里更新对应参考。不改变这些契约的内部重构不需要改正文，但参考页点名的符号被改名或移动时，链接要跟着改。
3. 跑 `check_refs.py` 和受影响页面的验证命令，报告实际跑了什么、没跑什么。以代码和 diff 为准，提交说明和 PR 标题只是作者的描述，和代码不一致时指出来，不要照着它改文档。
4. 刷新 `verified-at` 的规则：只有该页的验证命令跑通，并且已经按 diff 复核过正文，才更新为当前提交。复核后发现正文不用改，同样要刷新，这样“改过的源文件”提示才会消失。验证没跑通就保留旧值，并在 PR 里写明原因。
5. 按 [references/index-template.md](references/index-template.md) 里“描述语义变更”一节写 PR 说明：触发条件、改动前后的行为、链接到参考、实现和验证证据。
6. 文档和代码不一致时，按下面的分诊处理。

### 分诊

| 类别 | 判断 | 处理 |
| --- | --- | --- |
| 文档漂移 | 代码的现状是有意的，文档没跟上 | 改文档 |
| 验证缺口 | 文档里的验证命令本身有问题：路径或测试名写错、命令跑不了，或者测不到所说的行为 | 修正命令；确实没有测试就标“暂无”，并告诉用户 |
| 改动未完成 | 本次改动让原本通过的测试变红（例如重命名后测试还在调用旧名字） | 不是文档问题。在同一个改动里修好代码或测试；无权修改时报告给用户 |
| 行为退化 | 代码违反了文档写明的约束 | 不改文档，报告给用户并修代码 |
| 契约变更 | 改动需要放宽或删除一条约束 | 停下来问用户。Agent 不能自己认定“这是正常演进”。用户确认后再改约束，并写或更新一条 Agent Note |

不要为了让检查通过而删掉或放宽约束。

### 记录决策（note）

当一个决定的理由在代码、测试和现有文档里都看不出来，而且以后有人可能想“优化”掉它时，写一条 Agent Note。机械性或局部的改动不需要写。按 [references/agent-note-template.md](references/agent-note-template.md) 写，并在对应参考页的“决策”小节里链接过去。已有 Note 管这个决定的，就更新它，不要另写一份重复的。

### 定期巡检（maintain）

按 [references/maintenance.md](references/maintenance.md) 执行：先整理索引，再对每页做源码比对（可以用只读子代理并行），然后统一跑验证。结论只有三种：没有问题、提交一份修正、被阻塞（说明原因）。巡检只改文档，不改产品代码。

## 写作要求

- 写当前行为。历史放进 Git、PR 或 Agent Notes，计划放进 issue 或 PR。
- 链接到源文件和具名符号，不要粘贴会变的实现代码。签名本身看不出的含义（字段语义、单位、取值约束）要写清楚。
- 用相对链接，路径相对于参考页所在目录（例如 `../../src/x.ts`）。
- 引用其他章节时用章节名，不用编号。
- 文档更新本身证明不了实现是对的；行为变化仍然需要测试或运行证据。
